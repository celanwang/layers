# L4 Reference Diff Analysis: Mini Inference Engine

**Scope.** This is the L4-T1/T2 compare-and-read artifact. It uses the committed local implementation only after the blind implementation and Oracle checks, as required by the project cadence. No implementation, test, or existing benchmark file was changed.

**Evidence base.** Decode records are from Apple M4 Max / 48 GiB, MLX 0.32.4, FP32, 3 warmups and 10 repetitions. The T1 records have hashes `15cd4fbd762b` and `fa0b5fac54b5`. The newest T2 record is `engine-bench-20261021T115108Z.json`, hash `ac654603e49b`; earlier T2 runs remain in results and are not silently replaced. Local source references below use repository paths and line numbers at this commit.

## 1. Continuous-batching gain: scheduler and kernel batching are different effects

**Conclusion.** The newest 8-request measurement is 1.044× end-to-end (398.36 vs 381.53 output tokens/s), but it does not isolate bubble-free scheduling: all requests have the same 4-token prompt and 16-token output, and the measured run shares one prompt prefill; the mini engine still runs one model forward per request. See `results/l4/engine-bench-20261021T115108Z.json`, `results/l4/l4-t2-report.md` (“Key measurements” and its measurement caveat), `bench/l4_engine_bench.py:139-215`, and `layers/engine.py:226-260`.

The newest medians are 0.321320 s for continuous scheduling and 0.335489 s for sequential execution, a 14.169 ms end-to-end difference. This comparison removes seven repeated prompt prefills because all eight prompts match; it does not include staggered arrivals, uneven output lengths, or a replacement request arriving as another finishes. Therefore the spec's “1.04× from no-bubble scheduling” is not established by this experiment. The other retained T2 runs span 1.031×–1.062×, which also cautions against assigning the small gain to one isolated mechanism.

The kernel-batching opportunity can be bounded separately. One FP32 model forward reads about 52.5 MB of tied model weights (`13,126,656 parameters × 4 B`; `layers/model.py:28-70`; the L4 JSON records 52.5 MB). At eight independent decode forwards, the idealized weight traffic is 8 × 52.5 = 420 MB per scheduler iteration. A single batch-8 forward could reuse each weight matrix across eight token rows and approach one 52.5 MB weight read: 367.5 MB, or 87.5%, less weight traffic per eight output tokens. At the L0 small-workload bandwidth of 224.1 GB/s, the weight-only ceiling is 4,268 tokens/s for one sequence and 34.1k aggregate tokens/s for a perfect batch of eight. These are bandwidth ceilings, not an expected M4 result. If the observed sequential aggregate rate of 381.53 tokens/s retained its current efficiency and only gained the 8× weight reuse, the illustrative projection is about 3.05k tokens/s. The gap between 3.05k and 34.1k is the mini path's existing under-utilization plus other work; neither number is a vLLM prediction.

The structural cause is visible in `layers/engine.py:39-44,226-260`: `step()` iterates requests and calls `self.model(...)` separately for each one. By comparison, the vLLM scheduler schedules running and waiting requests in one iteration (`vllm/v1/core/sched/scheduler.py:3436-3881`), while PagedAttention's execution kernel reads KV blocks using the block table (`PagedAttention paper, §5`). The llama.cpp server likewise collects active slots into one shared `llama_batch` and invokes `llama_decode` (`tools/server/README-dev.md`, “Batching”; `include/llama.h`, `llama_batch` fields and `n_batch`/`n_ubatch`). Those designs provide a real batched model invocation that this mini engine lacks. The vLLM paper's reported 2–4× throughput gain is on its own GPU models and workloads, not a transferable multiplier for this M4 experiment.

## 2. Decode at 3.7% of the nominal roofline

**Conclusion.** The 3.7% figure uses the 450 GB/s large-array bandwidth denominator; the same measured run is 7.38% of the L0 224.1 GB/s small-workload bandwidth ceiling, and the source shows many small operations per token, but neither existing data nor a supported Metal trace lets us assign a measured fraction of latency specifically to kernel launch.

For the recorded `decode-bench-20261021T113854Z.json`, 256 generated tokens take 0.812790 s median, or 3.176 ms per generated token on the median run. The recorded roofline is 450 / 0.0525 = 8,571 tokens/s; 314.96 / 8,571 = 3.675%. L0's 2^24 FP32 add measured 224.1 GB/s, while its large add measured 450.6 GB/s (`results/l0/hw-profile-20261021T065826Z.json`, `runs/l0-hw-profile.md:8-18`). Replacing 450 with the small-task 224.1 gives a weight-only ceiling of about 4,268 tokens/s and 7.38% measured efficiency. A 52.5 MB weight read alone is about 0.234 ms at 224.1 GB/s, versus the observed 3.176 ms/token. The roughly 2.94 ms gap is not a pure launch measurement: it also contains low utilization of skinny matrix multiplies, attention and normalization operations, cache updates, sampling, host dispatch, and synchronization.

At the granularity asked for in the task, a single-token forward has **59 core stage slots**: per layer, Q/K/V projections (3), RoPE on Q and K (2), score/mask (1), softmax (1), probability-times-value (1), output projection (1), MLP's two projections plus GELU (3), and the two LayerNorms (2), giving 14 × 4 = 56; add embedding lookup, final LayerNorm, and the tied LM head. Add the two residual operations and K/V cache append per layer and the source-level total is **75 named op groups** (59 + 8 + 8). This is a static source-level count, not a profiler-reported GPU-kernel count. In the actual source, softmax expands to max/subtract/exp/sum/divide (`layers/attention.py:57-61`), RoPE and LayerNorm expand to elementwise/reduction expressions (`layers/attention.py:21-39`, `layers/transformer.py:24-31`), and the T1 cache concatenates K and V (`layers/inference.py:33-56`). MLX may fuse elementwise work, so counting each Python/MLX expression as a Metal launch would overstate launches. I attempted `mx.metal.start_capture()` for one cached token; MLX returned “Capturing is not supported.” `xctrace` is also unavailable in this environment. Thus the exact Metal launch count remains unmeasured; 75 is the requested operation-stage accounting, not a Metal-kernel trace.

The model executes 24 dense block projections per token (six per layer: Q/K/V/O plus two MLP projections), a final tied-vocabulary projection, reductions and elementwise work (`layers/attention.py:109-146`, `layers/transformer.py:34-50`, `layers/model.py:73-86`). The L4 one-token-forward curve in the two JSON records is roughly 1.93–2.23 ms at KV lengths 64–512; the cached decode loop also synchronizes sampling between model calls (`bench/l4_decode_bench.py:105-129`). L2 measured the naive attention path at 128 tokens around 0.36–0.39 ms per layer and its fast comparison around 0.18–0.19 ms (`results/l2/attention-bench-20261021T093939Z.json` and `...094129Z.json`). Together these observations support “small operations and dispatch/utilization are plausible dominant costs”; they do not prove that launch latency alone accounts for the remaining 92.6%.

For an external MLX-LM reference, a published M4 Max run reports 521.7 decode tokens/s for Granite-4.0-H 350M at 4-bit (`apple-silicon-llm-bench`, results table). Its protocol is mlx 0.32.2 / mlx-lm 0.31.3, 128 GiB, 132–145 prompt tokens, median of three processes, and the model reached EOS after 119 generated tokens. This is 26.7× more parameters, a hybrid Mamba-2 architecture, and quantized weights; it is useful as a public same-device ecosystem reference, not an apples-to-apples speed ratio. The closest size artifact found is a public 10M MLX TinyStories model card that demonstrates `mlx_lm.generate`, but reports training throughput rather than decode tokens/s. No public decode number for a roughly 13M model with matching precision and protocol was found in the sources checked. The current mlx-lm source uses a KV cache and invokes the model on one new token per normal generation step (`mlx_lm/generate.py:2764-3057`), so its path also highlights that batching/fused-kernel implementation details matter beyond the high-level cache interface.

## 3. Why the KV cache is nearly neutral here, and when it should help

**Conclusion.** The two existing cache-vs-uncached ratios straddle 1.0 (1.098× and 0.968×), while the context-length work/weight arithmetic predicts a crossover near 64 tokens and clearer gains around 128–256 tokens; this is a prediction for the next controlled measurement, not an L4 result.

The two raw T1 comparisons are not consistent enough to claim a repeatable speedup: for prompt 32 / max_new 32, config `15cd4fbd762b` measured 0.093867 s cached versus 0.103026 s uncached (1.098×); config `fa0b5fac54b5` measured 0.097695 s cached versus 0.094606 s uncached (0.968×). Both use 3 warmups and 10 repetitions, but differ in config hash and code commit, so their 1.031× geometric mean is only descriptive. The 64-to-512-token one-step cached rate falls by about 7–8% in both runs; that is the cache path's length cost, not a same-length uncached comparison.

For the decode benchmark's exact 32-token prompt and 32 decode calls, the uncached loop forwards lengths 32 through 63: 1,520 token positions total. The cached path processes 32 prompt positions and then 32 single-token positions: 64 total, 23.75× fewer token rows. Yet both paths still make about one model forward per generated token and read the model weights on each forward; the cached path does not avoid the dominant weight pass. For a dense forward with P parameters and n input rows, the weight-only arithmetic intensity is approximately 2Pn / (4P) = n/2 FLOP/B. At n=32–63 this is 16–31.5 FLOP/B, at or below the L0 balance point of about 32 FLOP/B. In that regime, removing recomputed rows can save FLOPs without lowering the weight-read floor, while the cache adds memory traffic and concatenation work.

A cache update must append K/V and attention must read the accumulated K/V. For this four-layer 512-wide FP32 model, the recorded paged-pool size is 16,384 B/token: 2.10 MB at n=128 and 8.39 MB at n=512 (`results/l4/engine-bench-20261021T115108Z.json`; consistent with the 2·n·d·dtype-per-layer formula in `results/l2/l2-attention-report.md`). T1's append materializes K and V with `mx.concatenate` on every step (`layers/inference.py:33-56`). Thus a simple cost model is:

- work removed by caching: roughly 24 L d^2 FLOPs for each old token row not re-run, plus the old-query attention work;
- traffic added/maintained by caching: at least 2 L d n s bytes for reading K/V, plus append/copy and layout costs, where L=4, d=512, s=4 B for FP32;
- crossover: compare saved-work time with K/V read/copy time and launch/dispatch overhead. The exact threshold depends on the effective M=1 versus M=n matmul throughput, which existing measurements do not isolate.

At n≈64, the uncached full-prefix forward reaches the L0 balance estimate (n/2≈32 FLOP/B). At n=128 it is about 64 FLOP/B, while cached decode still processes one input row (about 0.5 FLOP/B for the weight read) and K/V is only about 4% of the 52.5 MB weight payload. This predicts a more visible cache win from roughly 128–256 context tokens upward. A wider model also improves the weight-to-KV ratio because dense weights scale like Ld² while K/V bytes scale like Ldn; for example, doubling d to 1,024 at n=128 would make a four-layer FP32 KV read about 4.19 MB against roughly 210 MB of weights. This still needs measurement: large-context cached and uncached pairs are absent from results/l4, and the decode benchmark's model context setting differs from the 512-token KV-curve helper.

## 4. Paging and copy-on-write: same block size, different attention path

**Conclusion.** Our 16-token page matches vLLM's empirically selected default, and our fork/CoW saves 87.5% of prompt KV for the measured 8-way shared prefix, but our per-request gather path pays copy/dispatch costs that vLLM's paged attention kernel avoids.

The vLLM PagedAttention paper's §7.2 says block sizes 16–128 worked best on one ShareGPT trace, 16 and 32 worked on short Alpaca sequences, and it chose 16 as the default tradeoff between KV parallelism and fragmentation. The v0.6.2 CLI reference also lists 16 as the default. Our matching block size is evidence-aligned, not a hardware-tuned result for Apple M4; L4's seeded fragmentation check records 49 wasted token slots (802,816 B) for 8 sequences, under the aggregate 8×8-slot bound, while a single 16-token page can leave up to 15 slots (`results/l4/engine-bench-20261021T115108Z.json`, `results/l4/l4-t2-report.md`).

For 8 requests sharing a 32-token prefix, the benchmark allocates two 16-token pages once (524,288 B) instead of two pages per request (4,194,304 B): 3,670,016 B saved, 87.5%. The local pool increments page reference counts on fork and copies a shared page only on first write (`layers/paged_kv.py:150-224`). This maps directly to production use: common system prompts and prefix caching, multiple samples from one prompt, and beam search. PagedAttention §4.4 describes all three; its OPT-13B evaluation reports 37.6–55.2% KV-memory savings for beam search in one Alpaca workload and 44.3–66.3% in its ShareGPT experiment. Those production figures have different models/traces and should not be compared numerically to our synthetic 8×32 prefix test.

The read path differs materially. Our T2 adapter gathers page slices and concatenates multiple pages to produce contiguous K/V (`layers/paged_kv.py:308-336,351-362`) because attention consumes dense arrays (`layers/attention.py:129-146`). For a 128-token, four-layer cache, the K/V payload is 2.10 MB. Once it spans several pages, the returned gather logically copies that payload. Although `get()` constructs a gather before append, attention only reads the returned tensor shape to calculate the RoPE offset; the K/V data itself is unused. MLX operations are lazy and compute only values that are consumed, so this first gather should not materialize (`mlx/docs/src/usage/lazy_evaluation.rst`, “Only Compute What You Use”). The append result is consumed by attention, leaving one materializing gather per layer per step. A full gather's read-plus-write is about 4.19 MB and the attention read is another 2.10 MB: roughly 6.3 MB of logical traffic per step before page writes. This is a payload estimate, not measured DRAM traffic. The L4 T2 benchmark only reaches about 20 tokens, so its gather often stays within one or two pages and cannot validate the 128-token estimate.

PagedAttention instead passes the block table into an attention kernel and reads blocks in place; §5 describes assigning a GPU warp per block for coalesced access. That trades our repeated concatenate/copy for page-table indirection and kernel-side address calculation. llama.cpp's server API shows the other key production gap: it batches active slots' tokens for a shared `llama_decode`, with sequence IDs and positions in `llama_batch`, instead of making independent model calls.

## 5. Missing pieces and recommended landing points

**Conclusion.** L5 should quantify KV-precision tradeoffs; L6 should close the serving gap by adding true kernel batching, mixed prefill/decode scheduling and eviction, then evaluate speculative decode in that runtime.

| Missing piece | Evidence / impact in this iteration | Suggested landing |
|---|---|---|
| KV-cache quantization | FP32 uses 16 KB/token across four layers; BF16 halves that to 8 KB/token before scale metadata. mlx-lm exposes `kv_bits`, group size, and a quantization start point in `generate.py`. | **L5: quantization / mixed precision.** Add KV quantization after a baseline cache-accuracy check; measure memory, decode speed and logit drift. |
| Batched model forward and kernel-side paged attention | Eight independent forwards reread 8× the weights; current Engine loops over requests and gathers pages. | **L6: serving engine.** First add a batch-8 forward and validate cache/logit equivalence; then compare dense batching and direct page-table attention. |
| Prefill/decode mixing, admission, eviction/preemption | The mini engine prefills eagerly, has fail-fast capacity and no arrival queue (`runs/l4-implementation-notes.md:102-113`). vLLM's scheduler schedules running and waiting requests under token budgets and can preempt. | **L6: serving scheduler.** Introduce token-budgeted mixed steps and an explicit eviction/recompute policy; measure TTFT, inter-token latency and throughput under staggered arrivals. |
| Speculative decoding | Not implemented in the mini path. mlx-lm's public `speculative_generate_step` drafts multiple tokens, verifies them in the target model, then rewinds rejected cache slots. | **L6: advanced decode option.** Add only after batch scheduling works; require acceptance-rate and quality-equivalence measurements. |

## Deviation and limits

- No implementation, test, existing benchmark, or dependency changed. No test suite or lint command was run; the task's acceptance scope is documentary and excludes the suite. Metal capture was attempted, but the installed MLX reports capture unsupported and `xctrace` is absent, so the report gives 75 source-derived operation groups rather than claiming an exact GPU launch count.
- The exact requested same-size public MLX-LM decode figure was unavailable in the consulted sources. The closest public decode figure is a 350M model; it is explicitly marked as a non-comparable reference, and the same-order 10M source has no decode throughput.
- The requested 1.04× “scheduler no-bubble” attribution is not supported by the existing T2 protocol: the measured end-to-end comparison includes shared prefill and has no staggered arrivals or early-finishing requests. The report preserves that limitation instead of assigning the observed gain to unmeasured components.
