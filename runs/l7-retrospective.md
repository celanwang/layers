## 认知修正

1. **行相关项被削去 40%，但没有消失**。端点模型斜率 0.5022 → 0.30 ms/row（-38~40%），截距反升 +0.16~0.24 ms（物化固定成本）；B=8 行相关项仍占 56~58%。剩余最大候选是 page 写入/元数据 Python 循环（每 forward 32 次 `append_pages` + 256 次页表访问）与行级采样图构建——这些是结构定位，不是计时分配。
2. **小批量回归有机制解释**：B=1/短历史时旧 gather 只拼 3~6 个活页（单页可直接返回），而新路径的 bank 构建/编译图是固定成本，摊不薄。生产对应物：vLLM `forward_decode` 也按 `max_seq_len` 与 `num_seqs×num_heads` 选 V1/V2 kernel——"按形状分派"是生产惯例，不是缺陷。
3. **物化 ≠ 直读**：我们的向量化物化每 forward 跨 4 层仍有 32 MiB 写 / 64 MiB 读写的中间拷贝账；PagedAttention kernel 的"零拷贝"是**无中间连续前缀重建**（按页地址直读），且融合写入。MLX 无自定义 Metal kernel，这一层差距是框架边界，不是实现懒惰。
4. **假说判决的最终表述**：受控干预支持"host 小操作与同步是本工作负载的主要扩展约束"；不能声称"host 占剩余时间大头"（无 Metal trace）、不能外推到随机采样负载/更大模型/CUDA。判决再收紧一档的路径已明确（Metal capture 对齐 CPU 等待与 GPU 关键路径）。

## 开放问题（带入后续）

对照精读给出三个后续专项的性价比排序（`runs/l7-diff-analysis.md` §5）：

1. **Metal capture profiling**（0.5–1 天，首选）：回答"消除的 host 等待是否解释了大部分墙钟差、关键路径现在被什么占据"——判决收紧的最后一环，`mx.metal.start_capture` 本机可用。
2. **`mx.fast.scaled_dot_product_attention` 接入拼批 decode**（0.5–1 天）：预期仅几个百分点（attention 时间占比小），用 `valid[:,None,None,:]` 掩码；`mask="causal"` 在 q_len=1 不够。
3. **L5×运行时整合（INT8 页直读）**（profiling 之后再说）：L5 的 0.3× 教训在先——"省 4× 存储 ≠ 提速"，dequant-before-bank 无正面收益可辩护，融合压缩读取才是真路径（3–5 天）。
4. **历史挂账**（不变）：KV cache 转正条件配对测量（n≥256）、KV INT4/层敏感度、QAT。
